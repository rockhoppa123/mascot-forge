## 1. Context you must carry

**What v1.1 completed:**
- `-Spec parts-spec.json` data-drives P2 vocabulary (per-asset, no engine edit).
- `-AssetName` param drives all output filenames in `emit-svg-css.ps1`.
- `PART_IDS` derived from `rig.parts` in `emit.ts` (no hardcode).
- W3a: viewBox and source-path carried from spec.
- `check-all.ps1` runs 6 checks fail-fast, including a Land Rover regression cell.
- Item (4) — O(n²) scale guard — explicitly deferred to v1.2.

**The two v1.2 candidates:**

### Candidate A — Scale guard (O(n²) CCL)
`vectorize-pixel.ps1` uses a connected-component labelling step. The concern is that an
asset with many distinct colour regions (large n) could be slow because the current
implementation may be O(n²). This was explicitly flagged but NOT measured. ADR-0009 /
research-log Q7 item (4) deferred it with the note: "do NOT implement unless a real asset
hits >~3k rects."

The plan must answer:
- What is n actually? (colour regions, not pixels — how many did devbrain produce? land-rover?)
- Is the code actually O(n²), or is that a theoretical concern about a naive algorithm?
- Do any current or foreseeable assets (devbrain: 89 rects, land-rover: unknown) approach
  the threshold?
- YAGNI verdict: implement now, or leave the guard as a comment + doc?

### Candidate B — Proper CLI
Currently running the pipeline means calling raw pwsh one-phase-at-a-time:
```
pwsh tools/vectorize-pixel.ps1 -PngPath ... -OutDir ...
pwsh tools/segment-parts.ps1 -FlatSvg ... -Spec ... -OutDir ...
(human reviews segmentation)
pwsh tools/emit-svg-css.ps1 -SvgPath ... -RigPath ... -OutDir ... -AssetName ...
```
A CLI would wrap this into a single entry-point:
```
mf forge <asset-name>         # run all phases end-to-end (minus human-review step)
mf emit <asset-name>          # run P3+P4 only (post-review)
mf check                      # alias for check-all.ps1
```
Key decisions a CLI plan must resolve:

C1 — **Runtime**: Node.js (`commander`/`yargs`) vs a single PowerShell wrapper script vs
something else. Node is already present (emit-react-gsap uses ts/node). A pwsh wrapper
costs zero new deps. A Node CLI gets tab-completion and cross-platform paths but needs
packaging. The ponytail rule: what's the minimum that works?

C2 — **Scope**: full forge-to-emit pipeline wrapper, or just a `mf check` + per-phase
aliases? The human-review breakpoint (after P2 segmentation) means a truly linear
`forge` command can't be fully automated — a CLI must handle the pause gracefully.

C3 — **Asset convention**: where does the CLI look for assets? `assets/<name>/` convention
is already established. Does the CLI assume `assets/<name>/parts-spec.json` exists?

C4 — **Install**: `npm link` / `npx`? Or just `pwsh mf.ps1 forge devbrain`? Or a batch
wrapper in the repo root?

C5 — **Does `check-all.ps1` stay as-is**, or does the CLI subsume it?

asset, a CLI may be premature. Make the call.

path that works).

D4 — **v1.2 scope statement**: what is and is not in v1.2. Anything that would be
interesting but isn't in the candidates (e.g. auto-rigging research, Rive target, web UI)
